# 課金システム 設計書

作成日: 2026-07-13
前提: [要件定義書](./要件定義書.md)

## 1. 全体アーキテクチャ

```
admin (ブラウザ)
   │ ①契約ボタン
   ▼
Nuxt server route ──② Checkout Session作成──▶ Stripe
   │                                            │
   │◀─③ リダイレクトURL                          │
   ▼                                            │
Stripe Checkout(カード入力・契約完了)            │
                                                 │
Stripe ──④ Webhook(署名検証)──▶ /api/billing/webhook
                                     │
                                     ▼ ⑤ subscriptions テーブル更新 (service role)
                                 Supabase DB
                                     ▲
auth.global.ts / billing middleware ─┘ ⑥ アクセス制御はDBのみ参照
```

設計原則:

- **StripeがマスターデータでDBはキャッシュ**。ただしアプリの表示・アクセス制御は必ずDB(`subscriptions`)を参照し、リクエスト毎にStripe APIを呼ばない。
- 状態同期はWebhookで行い、欠落時は手動同期APIで復旧する。
- カード情報・決済UIはStripe Checkout / Billing Portalに全面委譲。自前の決済フォームは作らない。

## 2. DBスキーマ

マイグレーション: `supabase/migrations/2026XXXXXXXXXX_add_billing.sql`

### 2.1 billing_settings(全体で1行)

```sql
CREATE TABLE billing_settings (
  id INT PRIMARY KEY DEFAULT 1 CHECK (id = 1),        -- 単一行を強制
  monthly_price INTEGER NOT NULL,                      -- 最小通貨単位(JPYなら円、USDならセント)
  currency TEXT NOT NULL DEFAULT 'THB',
  trial_days INTEGER NOT NULL DEFAULT 14 CHECK (trial_days >= 0),
  stripe_product_id TEXT,                              -- 初回設定時に作成
  stripe_price_id TEXT,                                -- 料金変更ごとに新Priceを作成して差し替え
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### 2.2 subscriptions(店舗ごとに最大1行)

```sql
CREATE TABLE subscriptions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id UUID NOT NULL UNIQUE REFERENCES stores(id) ON DELETE CASCADE,
  stripe_customer_id TEXT UNIQUE,
  stripe_subscription_id TEXT UNIQUE,
  status TEXT NOT NULL DEFAULT 'none',
    -- 'none' | 'trialing' | 'active' | 'past_due' | 'unpaid' | 'canceled' | 'exempt'
  current_period_start TIMESTAMPTZ,
  current_period_end TIMESTAMPTZ,                      -- 次回請求日 / 解約時の利用期限
  trial_end TIMESTAMPTZ,
  cancel_at_period_end BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE billing_webhook_events (                  -- 冪等性担保用
  stripe_event_id TEXT PRIMARY KEY,
  type TEXT NOT NULL,
  processed_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

`status` はStripeのsubscription statusをそのまま採用し、独自値は `none`(未契約)と `exempt`(免除)のみ。

### 2.3 RLSポリシー

| テーブル | SELECT | INSERT/UPDATE/DELETE |
|---------|--------|---------------------|
| `billing_settings` | 認証済み全員(契約前の料金表示に必要) | なし(service roleのみ = server routeから更新) |
| `subscriptions` | 自店舗の行のみ(既存の店舗分離パターン `user_store_map` を踏襲) | なし(service roleのみ = Webhook/server routeから更新) |
| `billing_webhook_events` | なし | なし(service roleのみ) |

super_adminはserver route(`server/api/admin/`)経由でservice roleを使って全行を参照する。既存の `server/api/admin/stores.post.ts` と同じパターン。

## 3. Stripeオブジェクト設計

| Stripe | 対応 |
|--------|------|
| Product | 1つ(「rental-system 月額利用料」)。初回料金設定時に作成し `billing_settings.stripe_product_id` に保存 |
| Price | 料金変更のたびに新規作成(Stripe Priceは金額変更不可のため)。旧Priceはarchive |
| Customer | 店舗ごとに1つ。metadataに `store_id` を格納 |
| Subscription | 店舗ごとに1つ。Checkout(mode=subscription)で作成。`trial_period_days` = `billing_settings.trial_days` |
| Billing Portal | カード変更・請求履歴・解約(期間末解約のみ許可するPortal Configurationを使用) |

### 課金サイクル

Stripe標準の billing cycle anchor(サブスクリプション作成日 ≒ トライアル終了日)をそのまま使う。「利用開始日から翌月同日まで」「超過で次月開始」はStripeのデフォルト挙動と一致するため、**カスタムアンカーや独自の日付計算は実装しない**。月末開始(31日など)の短い月への丸めもStripeに委譲する。

### 料金変更時の既存契約への適用

super_adminが料金を変更したとき:

1. 新Priceを作成し `billing_settings.stripe_price_id` を更新(新規契約に即時適用)。
2. 有効な全Subscriptionに対し `subscription.items` を新Priceへ更新、`proration_behavior: 'none'` を指定 → **次回更新から新料金**が適用される。対象件数が多い場合に備えて逐次処理・失敗リトライをログに残す。

### 未払いフロー

Stripeダッシュボードの Smart Retries(自動リトライ、標準で最大4回/約3週間)を有効化し、最終リトライ失敗時のアクションを「サブスクリプションを `unpaid` にする」に設定する。

- `invoice.payment_failed` → status `past_due` に同期 → 画面に警告バナー(利用は継続可)
- リトライ失敗確定 → status `unpaid` に同期 → スタッフ画面をブロック(FR-11)

猶予期間の長さはコードではなくStripeのリトライ設定で制御する。

## 4. サーバーAPI設計

`stripe` npmパッケージを追加。`nuxt.config.ts` の `runtimeConfig` に `stripeSecretKey` / `stripeWebhookSecret` を追加(server専用)。

| ルート | 権限 | 内容 |
|-------|------|------|
| `POST /api/billing/checkout` | admin | 自店舗のCheckout Session作成。既存Customerがなければ作成。`success_url`/`cancel_url` は設定画面 |
| `POST /api/billing/portal` | admin | 自店舗のBilling Portal Session作成しURLを返す |
| `GET /api/billing/subscription` | admin/staff | 自店舗の課金状態(DBから)。バナー表示用 |
| `POST /api/billing/webhook` | 署名検証のみ | Stripe Webhook受信(下記) |
| `GET /api/admin/billing/settings` | super_admin | 料金設定取得 |
| `PUT /api/admin/billing/settings` | super_admin | 料金・トライアル日数の更新(Product/Price作成、既存契約の差し替え) |
| `GET /api/admin/billing/subscriptions` | super_admin | 全店舗の課金ステータス一覧 |
| `POST /api/admin/billing/exempt` | super_admin | 店舗の免除フラグON/OFF |
| `POST /api/admin/billing/sync` | super_admin | Stripe APIから全subscriptionを再取得しDBを補正(NFR-04) |

権限チェックは既存adminルートのパターン(サーバー側でJWTからrole判定)に従う。

### Webhookハンドラ

`readRawBody` で生ボディを取得し `stripe.webhooks.constructEvent` で署名検証。`billing_webhook_events` にevent IDを記録済みならスキップ(冪等)。

処理対象イベント:

| イベント | 処理 |
|---------|------|
| `checkout.session.completed` | customer/subscription IDを `subscriptions` に保存 |
| `customer.subscription.created/updated` | status・period・trial_end・cancel_at_period_end を同期 |
| `customer.subscription.deleted` | status = `canceled` |
| `invoice.payment_failed` | status同期(past_due)。将来の通知拡張ポイント |
| `invoice.paid` | status同期(active復帰) |

## 5. フロントエンド設計

### 5.1 アクセス制御(middleware)

`useStaff()` に課金状態を追加取得するのではなく、**新composable `useSubscription()`**(`GET /api/billing/subscription` の結果を `useState` にキャッシュ)を追加し、新middleware `billing.global.ts` を作成する。実行順は `auth.global.ts` の後(ファイル名のアルファベット順で auth → billing となる。※Nuxtのglobal middlewareはファイル名順実行のため命名に注意)。

```
billing.global.ts のロジック:
- 未ログイン / super_admin / 管理コンソール(/admin/**) → 何もしない
- 対象外パス(/login, /billing, /billing/blocked) → 何もしない
- status が trialing / active / past_due / exempt → 通過
- それ以外(none / unpaid / canceled):
    - admin → /billing へリダイレクト(契約・支払い修正ページ)
    - staff → /billing/blocked へリダイレクト(案内のみ)
```

### 5.2 画面

| 画面 | レイアウト | 内容 |
|------|-----------|------|
| `/billing`(新規) | default(サイドバーなし表示考慮) | admin用。未契約時: 料金・トライアル表示+「契約する」→Checkout。契約済み: ステータス・次回請求日・「支払い方法の管理/解約」→Portal。middleware: admin以上 |
| `/billing/blocked`(新規) | シンプル | staff用案内「店舗の契約が無効です。管理者に連絡してください」+ログアウト |
| `/settings` 拡張 | default | 「契約・支払い」セクション(admin表示のみ)に現在のステータスと `/billing` へのリンク |
| `/admin/billing`(新規) | admin | super_admin用。料金・通貨・トライアル日数の設定フォーム。`definePageMeta({ layout: 'admin', middleware: 'super-admin-only' })` |
| `/admin/stores` 拡張 | admin | 一覧に課金ステータス列+免除トグル+手動同期ボタン |
| 全ページ共通バナー | default layout | `past_due` のとき「お支払いに問題があります」警告(adminには `/billing` リンク付き) |

### 5.3 ステータス表示ラベル

| status | 表示 | 色 |
|--------|------|----|
| none | 未契約 | グレー |
| trialing | トライアル中(〜M/D) | 青 |
| active | 有効 | 緑 |
| past_due | 支払い遅延 | 黄 |
| unpaid | 停止中 | 赤 |
| canceled | 解約済み | グレー |
| exempt | 免除 | 紫 |

| 変数 | 用途 | 置き場所 |
|------|------|---------|
| `STRIPE_SECRET_KEY` | Stripe API(server専用) | `.env` / Vercel env |

## 7. テスト方針

- **ユニット**: Webhookハンドラのイベント別分岐・冪等性(vitest、Stripeイベントはfixture JSON)。
- **E2E(Playwright)**: Stripe本体はモックし、DBの `subscriptions.status` を直接seedして状態別のアクセス制御を検証する:
  - 未契約adminが `/` にアクセス → `/billing` へリダイレクト
  - 未契約staffが `/` にアクセス → `/billing/blocked`
  - `active` の店舗は従来通り全E2Eが通る(既存36テストの前提として、E2Eシード店舗を `exempt` または `active` に設定)
  - `past_due` でバナー表示
  - super_adminの料金設定画面の表示・保存
- **手動(Stripeテストモード)**: テストカード `4242…` での契約、`4000000000000341` での支払い失敗→リトライ→停止、テストクロックでの更新日検証。

## 8. リスクと対策

| リスク | 対策 |
|-------|------|
| Webhook欠落・順序逆転でDBとStripeが不整合 | イベントは常に「最新のsubscriptionオブジェクトで上書き同期」とし、差分適用しない。手動同期API(NFR-04)で復旧可能 |
| 既存E2E 36テストが課金ブロックで全滅 | E2Eシード店舗を `exempt` に設定するseedをマイグレーションに含める |
| middleware実行順の誤り | `billing.global.ts` はauth後実行をE2Eで固定検証 |
| 料金変更の一括Price差し替え失敗 | 対象subscription毎に結果をログし、失敗分は手動同期APIで再適用 |
